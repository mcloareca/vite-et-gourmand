1. Organisation

Projet réalisé seul, dans un délai court, avec une date de livraison imposée (19 novembre 2026, 23 h 59). J'ai choisi une méthode Kanban : simple à tenir seul, elle rend visible ce qui est fait, en cours et à faire, sans les cérémonies d'une méthode Scrum (sprints, réunions) qui n'ont pas de sens pour une personne.

Outil : tableau Kanban Notion, lien public : [à compléter]

Colonnes : À faire → En cours → Terminé. Une carte = une fonctionnalité ou un livrable, avec une catégorie (Analyse, Conception, Front-end, Back-end, Sécurité, Tests, Documentation, Déploiement) et une priorité.

2. Priorisation (MoSCoW)

PrioritéSignificationExemples
MustExigé par l'énoncé : sans cela, le projet n'est pas conformeCommande, deux bases de données, sécurité, déploiement, livrables
ShouldImportant mais contournable temporairementEnvoi réel des e-mails (affichés dans les journaux en attendant)
CouldAmélioration si le temps le permetPhotos réelles, audit RGAA complet, modification d'une commande par un employé

Règle : une carte Should ou Could ne passe « En cours » que si toutes les cartes Must de la même étape sont terminées.

4. Suivi de la conformité

Le fichier docs/MATRICE_CONFORMITE.md du dépôt reprend chaque exigence de l'énoncé, l'endroit du code qui y répond et la façon dont elle a été vérifiée. Trois états sont distingués : testé, codé mais non testé, à faire. Le fichier docs/SUIVI.md note, à chaque étape, ce qui est terminé, ce qui reste à vérifier et ce qui reste à faire.

5. Gestion des versions (Git)

  • main : version stable, déployée automatiquement sur Render.
  • develop : intégration.
  • feature/… : une branche par fonctionnalité, créée depuis develop, fusionnée avec --no-ff après les tests (npm test).
  • develop est fusionnée dans main une fois testée.

Branches de fonctionnalité utilisées : feature/base-de-donnees, feature/regles-metier, feature/application, feature/documentation, feature/deploiement, feature/livrables.

6. Risques identifiés

RisqueRéponse
Délai très courtPriorisation MoSCoW ; architecture simple ; tests automatiques pour ne pas régresser
Expiration d'une base gratuite avant l'évaluationNeon et Atlas plutôt que le PostgreSQL gratuit de Render (expire après 30 jours)
Serveur en veille pendant la correctionSignalé dans le manuel ; ouvrir le site une minute avant la démonstration
Indisponibilité de l'API AdresseMessage clair au client ; la commande est refusée plutôt que mal facturée
MongoDB indisponible lors d'une commandeLa commande est enregistrée dans PostgreSQL ; npm run sync-stats resynchronise sans doublon
