1. Réflexions initiales

Le besoin : une application web permettant à un traiteur de présenter ses menus, de prendre des commandes en ligne et de les suivre jusqu'à la livraison, avec trois espaces (utilisateur, employé, administrateur). L'énoncé impose une base relationnelle et une base non relationnelle, le déploiement en ligne et le respect du RGAA et du RGPD.

Principes retenus :

  • Simplicité : une seule application, un seul langage (JavaScript) côté serveur et côté navigateur, pas de framework front-end. Chaque fonctionnalité se lit dans un seul fichier de route.
  • Le serveur fait foi : les pages sont générées côté serveur ; toutes les règles (prix, distance, statuts, droits) sont vérifiées par le serveur.
  • Amélioration progressive : les formulaires fonctionnent sans JavaScript ; JavaScript ajoute le filtrage sans rechargement, le prix en direct et le graphique.

8. Diagramme de séquence : connexion

sequenceDiagram
  actor U as Utilisateur
  participant S as Serveur Express
  participant P as PostgreSQL
  U->>S: POST /connexion (e-mail, mot de passe, jeton CSRF)
  S->>S: Limite : 10 échecs / 15 min / IP
  S->>P: SELECT utilisateur WHERE email = $1
  P-->>S: Compte (hash, rôle, actif)
  S->>S: bcrypt.compare(mot de passe, hash)
  alt Incorrect ou compte désactivé
    S-->>U: 401 « E-mail ou mot de passe incorrect »
  else Correct
    S->>S: session.regenerate() puis rôle en session
    S->>P: Enregistre la session (table session)
    S-->>U: Cookie httpOnly + redirection vers son espace
  end

9. Sécurité

RisqueMesure
Injection SQLRequêtes paramétrées ($1, $2) dans toutes les requêtes
XSSÉchappement EJS <%= %>, textContent en JavaScript, en-tête Content-Security-Policy (scripts du site uniquement)
CSRFJeton aléatoire par session vérifié sur chaque POST ; cookie SameSite=Lax
Mots de passeRègle de complexité vérifiée côté serveur, hachage bcrypt, jeton de réinitialisation haché (SHA-256), valable 1 h, à usage unique
Force bruteexpress-rate-limit sur connexion, inscription, réinitialisation et contact
SessionsStockées en base, cookie httpOnly et Secure en production, régénérées à la connexion, expiration 2 h, supprimées à la désactivation d'un employé
Contrôle d'accèsMiddlewares exigerConnexion et exigerRole ; filtre utilisateur_id sur les commandes d'un client ; rôle employé imposé côté serveur à la création ; aucun moyen de créer un administrateur
Falsification de donnéesValidation serveur de chaque champ ; prix, distance et ville recalculés par le serveur ; images limitées aux fichiers existants
Clickjacking, détection de typeX-Frame-Options: DENY, frame-ancestors 'none', X-Content-Type-Options: nosniff
Fuite d'informationsMessages d'erreur génériques ; mêmes réponses pour un e-mail existant ou non ; secrets en variables d'environnement

10. Tests

  • Tests unitaires automatiques (npm test, 14 tests) : calcul du prix (minimum, seuil de réduction, livraison, arrondis), règles de mot de passe, e-mail, téléphone, distance.
  • Tests de bout en bout (script de vérification HTTP, 65 vérifications, exécuté en local le 18/11/2026) : parcours visiteur, inscription, commande, espaces utilisateur, employé et administrateur, CSRF, contrôles d'accès.
  • Vérifications manuelles dans Chrome : filtrage sans rechargement, prix en direct, affichage mobile (390 px), console sans erreur.

11. Déploiement

Étapes détaillées dans le dépôt : docs/GUIDE_COMPTES.md et docs/DEPLOIEMENT.md.

  1. Le code est poussé sur GitHub (branche main).
  2. La base PostgreSQL est créée sur Neon (Francfort) ; npm run init-db exécute creation.sql puis donnees.sql.
  3. Le cluster MongoDB Atlas (Francfort) est créé ; un utilisateur dédié et l'accès réseau sont configurés ; init-db y copie les commandes.
  4. Render crée le service à partir du fichier render.yaml (Blueprint) : npm install puis npm start, Node.js 24, offre gratuite.
  5. Les secrets (DATABASE_URL, MONGODB_URI, SMTP) sont saisis dans Render ; SESSION_SECRET est généré par Render.
  6. Chaque git push sur main redéploie automatiquement.

Limites de l'hébergement gratuit : mise en veille du serveur Render après 15 minutes sans visite (premier chargement d'environ une minute) ; 1 Go pour PostgreSQL (Neon) ; 512 Mo pour MongoDB (Atlas).

12. Limites connues

  • Distance de livraison calculée à vol d'oiseau, plus courte que par la route.
  • Les employés ne modifient pas le contenu d'une commande (seulement son statut ou son annulation motivée).
  • Pas de suppression de compte en libre-service : sur demande via le formulaire de contact.
  • Images de démonstration : illustrations simples, à remplacer par de vraies photographies.
